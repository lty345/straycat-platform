# 表结构设计（MVP 最简版）

> 设计原则：**每张表只保留 MVP 跑通必需的字段**。能删的全删了，缺的以后加。
> 判断标准：这个字段被"首页列表/详情页/推荐排序/领养抢占"四件事中的哪一件用到？
> 一件都没用到 → 不加。

---

## 一、`app_user` 用户（最小版）

冷启动要存兴趣标签，所以得有这张表。**不做密码、不做登录**——MVP 阶段用户由前端/测试直接传 id。

| 字段 | 类型 | 可空 | 默认 | 说明 |
|---|---|---|---|---|
| id | INT PK 自增 | 否 | — | |
| nickname | VARCHAR(50) | 是 | NULL | 昵称 |
| city | VARCHAR(50) | 是 | NULL | 城市，用于同城加权 |
| interest_tags | VARCHAR(255) | 是 | NULL | 兴趣标签，**逗号分隔**，如 `橘猫,救助,科普` |
| create_time | DATETIME | 否 | now() | |

**索引**：无（数据量小，按 id 查就够）

```python
__tablename__ = "app_user"
```

## 二、`content` 内容

| 字段 | 类型 | 可空 | 默认 | 说明 |
|---|---|---|---|---|
| id | INT PK 自增 | 否 | — | |
| title | VARCHAR(200) | 否 | — | 标题 |
| summary | VARCHAR(500) | 是 | NULL | 摘要，**列表页只查这个，不拉 body** |
| body | TEXT | 是 | NULL | 正文，详情页才查 |
| tags | VARCHAR(255) | 是 | NULL | **逗号分隔**，如 `橘猫,救助` |
| mood | VARCHAR(16) | 是 | NULL | 情绪基调：治愈 / 科普 / 揪心 / 欢乐 |
| cover_url | VARCHAR(500) | 是 | NULL | 封面图 URL（MVP 不做上传） |
| pub_time | DATETIME | 否 | now() | 发布时间，**时间衰减靠它** |
| create_time | DATETIME | 否 | now() | |

**索引**：

| 索引 | 为什么 |
|---|---|
| `idx_pub_time (pub_time)` | 推荐要按"最近发布"排序 + 时间衰减计算 |
| `idx_mood (mood)` | 按情绪筛选 |

## 三、`cat` 待领养的猫

| 字段 | 类型 | 可空 | 默认 | 说明 |
|---|---|---|---|---|
| id | INT PK 自增 | 否 | — | |
| name | VARCHAR(50) | 否 | — | 名字 |
| breed | VARCHAR(30) | 是 | NULL | 品种，如 橘猫 / 狸花 |
| age_month | INT | 是 | NULL | 月龄 |
| health | VARCHAR(50) | 是 | NULL | 健康状态（已驱虫/已绝育/…） |
| city | VARCHAR(50) | 是 | NULL | 所在城市，用于同城 |
| status | VARCHAR(16) | 否 | '待领养' | **待领养 / 审核中 / 已领养** |
| applicant_id | INT | 是 | NULL | 当前申请人（抢占成功后写入） |
| content_id | INT | 是 | NULL | 关联的介绍内容（可不填） |
| cover_url | VARCHAR(500) | 是 | NULL | 照片 |
| create_time | DATETIME | 否 | now() | |

**索引**：

| 索引 | 为什么 |
|---|---|
| `idx_status_city (status, city)` | 列表页"同城待领养"就是这个查询 |
| `idx_applicant (applicant_id)` | "我申请了哪些猫" |

**★ 领养抢占怎么做（MVP 不建申请表）**

不要加"申请记录表"，直接用一条原子 UPDATE：

```sql
UPDATE cat SET status='审核中', applicant_id=? 
WHERE id=? AND status='待领养'
```

- `rowcount == 1` → 抢到了
- `rowcount == 0` → 被别人抢先

**这就是你挂号系统里那套防超卖的同款写法。** 一个“申请记录表”是下一版的事。

## 四、`user_event` 埋点（推荐的燃料）

| 字段 | 类型 | 可空 | 默认 | 说明 |
|---|---|---|---|---|
| id | BIGINT PK 自增 | 否 | — | 写多读少，用 BIGINT |
| user_id | INT | 否 | — | 谁 |
| target_type | VARCHAR(16) | 否 | — | `content` / `cat` |
| target_id | INT | 否 | — | 哪个 |
| event | VARCHAR(16) | 否 | — | `view` / `like` |
| duration_ms | INT | 是 | NULL | 停留时长（view 时可带） |
| create_time | DATETIME | 否 | now() | |

**索引**：

| 索引 | 为什么 |
|---|---|
| `idx_user_time (user_id, create_time)` | **最重要**：推荐要"这个用户最近看了什么" |
| `idx_target (target_type, target_id)` | 统计某条内容的热度 / 点赞数 |

**★ 为什么用 `target_type + target_id` 而不是两个字段**

以后点赞对象可能是 content，也可能是 cat。加一个类型值就够了，不用改表结构。

**★ 为什么 user_id 不设外键**

埋点要求"写入极快、丢几条不致命"。外键每次插入都要校验另一张表，会拖慢写入。
**内容/订单要外键，日志/埋点不要**——这是通用判断。

## 四张表的关系

```
app_user ──(user_id)──> user_event ──(target_id)──> content / cat
                                                    ↑
content ──(content_id)──────────────────────────────┘  (猫的介绍文章)
cat ──(applicant_id)──> app_user                (谁抢到了)
```

**没有多对多，没有联表查询。** 推荐的打分全部在 Python 里算——数据量小的时候这样最简单，也最好解释。

## 我故意简化掉的东西（以及什么时候该改）

| 简化 | 什么时候必须改 |
|---|---|
| `tags` 用逗号分隔（不是关联表） | 内容超 1000 条、或要"按标签统计"时 → 拆 `content_tag` 表 |
| 不做申请记录表（只用 `cat.applicant_id`） | 要保留"申请历史/多轮审核"时 |
| 不做点赞去重（同一人可重复 like） | 要精确点赞数时 → `user_event` 加 `UNIQUE(user_id,target_type,target_id,event)` |
| 不做软删除 | 要支持"撤销删除"时 → 加 `is_deleted` |
| 用户不登录、无密码 | 接真实用户体系时 |
| 无 `update_time` | 需要"最近修改"审计时（加一列 `ON UPDATE CURRENT_TIMESTAMP`） |

**"什么时候改"比"改成什么"重要。** 面试被问"为什么这么设计"，你答这句话就是加分。

## 写模型时的注意事项

1. **一个表一个文件**，放 `db/model/`，文件名首字母大写（`Content.py` / `Cat.py` / `UserEvent.py` / `AppUser.py`）
2. **每张表建完要去 `db/model/__init__.py` 里 import 一次**，否则 `create_all` 见不到它
3. 字段名和这里保持一致（推荐算法里有大量按字段取值的代码，改名字会很痛）
4. `status` / `mood` / `event` 这类枚举值，**把取值写进 `comment=`**，别让后来的人猜
5. 建完跑 `python main.py`，然后用 `SHOW CREATE TABLE 表名` 核对一下索引是否真的生成了
